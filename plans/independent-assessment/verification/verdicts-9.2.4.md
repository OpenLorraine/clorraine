## New finding (for a different verification session)

### ASM-WS5-023 — `clipboardWrite` reports success for raw data that the 3.1 clipboard device discards, so `clipboardRead` never sees it

- **Severity**: Major
- **Confidence**: verified
- **Lens**: A1200 shipped (`hosted-amiga`, `std.amiga.clipboard`); other 2.0+ versions not tested
- **Location**: `compiler/runtime/shim_hosted_amiga_optional_services.c:658-685` (`cl_clipboard_write`: raw `CMD_WRITE` of the caller's bytes, then `CMD_UPDATE`, returns TRUE), `stdlib/std.amiga.clipboard.clo:34-40` ("Writes the whole clip and marks it current; true on success"), at e24a8752
- **Checklist item**: WS5-06 (also WS5-04)
- **Author session**: ses_dea9a6107ffefWXd6gFWNJQszZ
- **Evidence**: Reproduction on A1200/KS3.1 with the licensed Workbench 3.1 `Devs/clipboard.device` (6944 bytes) and `Assign CLIPS: RAM:` (directory drive `build/tmp/assessment/verify/a1200/cclipi`, runner `build/tmp/assessment/verify/run-a1200.sh`). The C control `src/clipiff.c` writes with the shim's exact sequence (`io_ClipID = 0`, `CMD_WRITE`, `CMD_UPDATE`); `src/clipdump.c` reads per the autodoc (`io_ClipID = 0`, offset 0, then reads to the end). Raw 4 bytes: `w raw: write 0 update 0 id 2`, then `dump: err 0 actual 0 id -1`, so no clip is readable. The same 4 bytes wrapped as `FORM…FTXT CHRS`: `w iff: write 0 update 0 id 2`, then `dump: … actual 24 id 1 bytes 70 79 82 77 …`, and the shim's own `clipboardRead` (`src/clipr.clo`) then returns `clipr 16 70`. With the shim: `src/clipw.clo` prints `second program write true`, yet the following dump reads 0 bytes (`a1200/cclipd`). `src/clipc.clo` (write, write, read in one program) reads `r2 0`.
- **Impact**: a program that copies text or bytes with `clipboardWrite` gets `true`, but nothing reaches the clipboard, and `clipboardRead` on raw data always returns 0. The `sdk-a600-addons` gate asserts only the write's return value (`clip: ok n 4`), so it cannot catch this.
- **Root cause**: the wrapper treats the clipboard as a raw byte store. On this system the clipboard device keeps only IFF clips, and the device's success codes do not report a discarded clip.
- **Recommendation**: wrap text in an IFF `FTXT`/`CHRS` clip on write and unwrap on read (or expose an IFF-level API and document it); make the gate read the clip back from a second program; or document that raw clips are unsupported and return false.
- **Effort**: S
- **Related**: ASM-WS5-016 (the same read path hangs a later write); ASM-WS8-002 (gate asserts a weaker property)
