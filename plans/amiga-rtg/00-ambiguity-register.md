# Ambiguity Register: Amiga RTG

> **Document**: 00-ambiguity-register.md
> **Parent**: [Index](00-index.md)

| ID | Category | Question | Options | Decision | Status / evidence |
|---|---|---|---|---|---|
| AR-1 | Scope | Which RTG stack is in scope? | A: Picasso96. B: CyberGraphX. C: both. | **A — Picasso96.** The user approved the Aminet Picasso96 package. CyberGraphX/CGX4 is explicitly dropped as a product row (2026-11-06); a single stack keeps the gate and ownership rules honest. No CGX media, licensing, or emulator work is planned. | ✅ Resolved — user approval 2026-11-06; P96 API/autodoc examined |
| AR-2 | Scope | Which card and baseline? | A: FS-UAE `uaegfx`. B: real Picasso IV. C: both. | **C — both, emulated only.** UAEGFX proves 32-bit true alpha on A1200/KS3.1. The emulated Picasso IV Zorro III card proves 24-bit truecolor with the real-card P96 driver on A4000/KS3.1. Physical cards need hardware and are not part of this row. | ✅ Resolved — both gates green; spike `build/rtg/probe` and `04-picasso-iv-gate.md` |
| AR-3 | Registry | How is the old `SDK-OPT-004` placeholder represented? | A: keep it in `9-optional` and set done. B: remove it and add a dedicated `10-rtg` bundle. | **B — dedicated `10-rtg` bundle with `SDK-RTG-001`.** Bundle 9 remains 20/20; RTG has its own plan, issue, baseline, and evidence. The user authorized the registry change from `wont` to a planned row. | ✅ Resolved — user approval 2026-11-06 |
| AR-4 | Naming | What is the module called? | A: `std.amiga.rtg`. B: `std.amiga.picasso96`. | **B — `std.amiga.picasso96`.** The surface is one stack, not a generic RTG abstraction. The name keeps CyberGraphX out of the contract and matches the library it wraps. | ✅ Resolved — existing per-library naming (`std.amiga.bsdsocket`, `std.amiga.amigaguide`) |
| AR-5 | Media | Where does the gate get P96? | A: commit the Aminet archive. B: expect the licensed/user-provided archive under `${AMIGA_DATA}/picasso96`. | **B.** The user approved the Aminet package; the archive is not committed. The gate extracts it into `build/`, verifies SHA-256 `0146d4a2aaadb82ec454dde6ca4fb33a3f646ca4c0daa46e569c025f4d9728af`, and documents the missing-media failure. | ✅ Resolved — user approval; archive hash verified |
| AR-6 | API | What is the minimum complete surface? | A: screen, bitmap, mode query, pixels, blit, RGB readback. B: also PIP/overlay, CLUT palettes, hardware sprites. | **A.** The issue's proposed scope is screen/mode, bitmap, write/blit, query, close. The gate can prove A; B would be unproven surface area. | ✅ Resolved — issue #11 proposed scope |
| AR-7 | Depths | Which pixel depths are supported? | A: 32-bit truecolor only. B: 24- and 32-bit truecolor. C: 15/16/24/32. D: also 8-bit CLUT. | **B — 24- and 32-bit truecolor.** UAEGFX proves 640x480x32; the emulated Picasso IV proves 640x480x24, the card's native format. 15/16-bit modes and CLUT palette ownership remain unproven and excluded. | ✅ Resolved — UAEGFX mode `50031303` depth 32; PIV mode depth 24 format 3 |
| AR-8 | Bitmap fill | How is an offscreen bitmap filled? | A: `p96RectFill`. B: a bounded `p96WritePixel` loop. | **B for bitmaps.** The spike showed `p96RectFill` does not round-trip the pure-blue value on a user-private A8R8G8B8 bitmap; the pixel loop does. Screen fills use `p96RectFill`, which round-trips. | ✅ Resolved — spike report `bitmap ff` after the loop |
| AR-9 | Capture | What artifact proves the gate? | A: CSCR/planar capture. B: PPM/P6 RGB readback. | **B — PPM.** RTG screens are chunky/truecolor; a CSCR writer would misrepresent the bitmap. `p96ReadPixelArray` produces RGB bytes, and the host checks the header and known pixels. | ✅ Resolved — spike `rgb 255 255 0 ...` |
| AR-10 | Errors | What happens when P96 or a mode is absent? | A: trap. B: return null/false/0. | **B.** Acquisition returns nullable handles; queries return 0/false; every shim entry validates its handle and bounds. This matches the existing optional modules. | ✅ Resolved — project convention |
| AR-11 | Header | How does the shim get P96 declarations? | A: add the P96 developer archive to every build. B: vendor a minimal attributed header. | **B.** `compiler/runtime/picasso96.h` carries only the constants, structs, and call macros used by the shim, derived from the CC-BY P96 developer package; `THIRD_PARTY_NOTICES.md` records the attribution. | ✅ Resolved — no build-time external include path |
| AR-12 | Toolchains | Must the RTG shim compile with vbcc? | A: GCC only, documented. B: both GCC and vbcc. | **B — both builds.** GCC uses fixed-argument `LP*` calls; vbcc uses plain prototypes and the SDK `amiga.lib` P96 stubs. The full P96 varargs macros are omitted because vbcc rejects them. The runtime gate is GCC; the corpus leg builds the RTG unit with both toolchains. | ✅ Resolved — vbcc rejects only the full P96 varargs macros; fixed-arg calls are the design |
| AR-13 | Tests | What is the evidence split? | A: only a runtime gate. B: spec, impl, and runtime gate. | **B.** Spec tests derive from the requirements (profile rejection, exports, cross-build); impl tests pin the shim/ownership; the gate proves the runtime report and PPM. | ✅ Resolved — project testing standard |
| AR-14 | Memory | Who owns the P96 screen and bitmap? | A: caller-managed raw pointers. B: opaque handles with generated drops. | **B.** `RtgScreen` and `RtgBitmap` are `freedBy` handles; each close/free is null-safe and exact-once. | ✅ Resolved — existing handle pattern |
| AR-15 | Limits | What is explicitly not claimed? | A: full P96. B: named subset. | **B.** No CyberGraphX, physical-card drivers, PIP/video overlay, CLUT palette editing, font/text rendering, hardware sprites, or a Workbench screen-mode preference UI. The emulated Picasso IV driver is the only real-card path claimed. | ✅ Resolved — recorded in `docs/known-limitations.md` |
| AR-16 | Picasso IV bus | Which emulated Picasso IV variant? | A: Zorro II on A1200. B: Zorro III on A4000. | **B — Zorro III on A4000.** Both variants run the 24-bit demo once the card driver, chip driver, monitor icon, and settings attachment are staged. Z3 is the card's native 32-bit aperture and the normal real-hardware configuration, so the committed gate uses A4000/Z3; the A1200/Z2 probe remains supporting evidence. The `picasso-iv-z2` spelling is invalid in FS-UAE 3.1.66 and is silently ignored; use `picasso-iv` for auto/Z2. | ✅ Resolved — `rtg: ok boards 1 mode 640x480x24 ...` on A4000/Z3 and A1200/Z2 |
